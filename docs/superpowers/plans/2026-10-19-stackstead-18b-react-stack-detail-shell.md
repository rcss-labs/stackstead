## Global Constraints

- Behaviour parity with `StackDetail.svelte` for everything this plan renders: not-found view with `Back to stacks` link to `/`; first-load failure banner `Could not load the stack` + `Retry`; `Showing the last loaded state` warning after a later failure; parse-error banner (`Compose file is missing` / `Compose file cannot be parsed`, message in a `pre`, guidance line); lifecycle buttons soft-disabled through `lifecycleDisabledReason({ live, parseError })` or `BUSY_REASON` while an operation of this stack runs or an action is in flight; `Remove` soft-disabled only while busy; success navigates to `?tab=operations&op=<id>` and tracks the operation; 409 → warning toast, other → danger toast, 503 → `refreshStatus()`; `?op=` preselect streams the operation; the stack vanishing after a remove is a successful removal (toast + `/`).
- Stores are not duplicated: the screen reads the controller's stores and `live`, `runningOps` through `useStore`; `useStackDetail` holds the controller in a lazy `useState` and starts/stops it in one effect; no React state mirrors `detail`, `operations`, `health` or `compose`.
- Every in-page navigation (rail, chips, timeline names, tabs, operation rows handled by `Link`) goes through `guarded()` → `navigate(itemHref(...))`; with no dirty editors it navigates at once; the `Discard unsaved changes?` `ConfirmDialog` is wired now and exercised in 18d / 18e. `setUnsavedChanges(false)` on unmount.
- Live metrics: `useLiveMetrics` acquires only while `detail && !parseError && (wide || serviceTab === 'metrics')`, `wide` from `mediaQuery('(min-width: 760px)')` through `useStore`; released in the effect cleanup and on unmount; never acquired while loading, failed or not found.
- Eagerness: `routes/StackDetail.tsx` stays `React.lazy`; everything under `app/detail/` is reached only from it; no `uplot` or `cm` import anywhere in this plan; the entry line is recorded after every task and must not move (≤ 104.1 kB gz from 18a).
- CSS Modules with tokens only; motion in module keyframes (`fadeUp` .22 s page, .18 s tab content, rail cpu bar `width .6s ease`, LED pulse via `Led`), neutralised by the 16a reduced-motion rule; classes never asserted in tests — roles, names, `aria-*`, `data-*` (`data-tone`, `data-pulse`, `data-selected`, `data-item`, `data-state`).
- Accessibility: one `h1`; the timeline is a `region` labelled `Health · last 60 min` (visible `PanelLabel` as its label) whose service names are buttons and whose bars are `img` with the lane's summary as `aria-label` (`<service>: healthy 55 min, unhealthy 5 min`); the rail is `nav` labelled `Services`; the service tabs use `Tabs` with `ariaLabel="Service sections"`; the rail footer totals are a `dl`; every target ≥ 40px under 760px (chips 36px tall with 2px vertical margin → 40px hit area, header buttons 40px).
- Test-first, conventional commits, no code bodies in this plan.

## Review Focus

1. Keyed route: navigating from `/stacks/a` to `/stacks/b` restarts the controller (new `GET /api/stacks/b`, a's health / log / live streams aborted, a's `?op=` not carried), and the title follows. (Task 1.)
2. Lifecycle safety on the header: every lifecycle button and Remove respect busy / compose / parse reasons as `title` + `aria-disabled`, a double click sends one request, success tracks the operation and lands on its panel, failures toast with the right kind and 503 refreshes the status. (Task 1.)
3. Timeline fidelity: lanes follow the stack's service order, segment widths are the run weights, tooltips read `<state> · <n> min`, only a trailing danger run pulses, a service missing from the response is outlined `nodata`, and the lane name selects the service through the guard. (Task 2.)
4. Live-stream conditions: no `metrics/live` request while loading, failed, not found or under a parse error; one stream when wide; the stream opens and closes with the viewport and with the Metrics tab; the Metrics tab and the rail share it; unmount aborts it. (Task 3.)
5. Operations: `?op=` preselects and streams, the list ticks only while something runs, `Cancel` calls the API once per click, `done` events refresh stacks / running ops and reload the detail, and a removal's `done` leaves the page with one success toast. (Task 4.)
