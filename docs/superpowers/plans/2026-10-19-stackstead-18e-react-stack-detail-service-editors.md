# Stackstead Plan 18e — React stack detail (e): service editors — form, edit, add, remove, network picker, file browser

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **Plan format:** tasks, names, signatures, test cases and examples only; no code bodies. Implementers write everything test-first.

**Goal:** Fill the last two slots of the stack detail — the service header's `Edit` and the rail's `+ Add` — with the structured editors ported from Svelte: `ServiceForm` (source, ports, volumes, environment with `.env` paste, networks, network mode, healthcheck, restart, limits; read-only groups with the raw-editor hint; error announcement and focus), `NetworkPicker` (API networks with subnet hints, static IP, free-text fallback, `Create network…` through `CreateNetworkDialog`), `FileBrowser` (roots, breadcrumbs, dir / file picks, error wording, stale responses), `ServiceEditor` (preview → save with hash → Apply with an inline operation panel; 409 reload / discard with rebase notices; 422 raw-editor hand-off; 503 status refresh), `AddServicePanel` (name + form, review, conflict flow, next-Up guidance) and the **Remove service** flow at the bottom of the editor pane — with every `ServiceForm`, `ServiceEditor`, `AddServicePanel`, `NetworkPicker`, `FileBrowser`, `CreateNetworkDialog` and page-level `service membership` behaviour ported as `.test.tsx` cases, and the editors' dirty flags feeding the unsaved-changes guard from 18d.

**Architecture:** Reusable form pieces go under `web/src/app/stacks/` (Plan 20's New stack composes `ServiceForm`, `NetworkPicker` and `FileBrowser`; Plan 22 reuses `CreateNetworkDialog` from `web/src/app/networks/`). `ServiceForm` is controlled: `form` / `onChange(form)` (+ `name` / `onNameChange`) instead of Svelte's `bind:form`, with `errors` from the parent and an imperative `focusFirstError()` through `ref`. `ServiceEditor` and `AddServicePanel` (under `web/src/app/detail/`) bind the existing `createServiceEdit` / `createServiceAdd` state machines (lazy `useState`, stores through `useStore`), mirror the machine's `form` store into the controlled form and push snapshots back on change, and report `dirty` through `onDirtyChange`. The screen owns `editingService` / `addingService`, renders the editor in place of the service pane's tabs (and the add panel in place of the right pane), routes `Edit` / `+ Add` / `Close editor` through `guarded()`, and keeps the editor mounted across detail refetches (keyed on `<stack>/<service>`, never on the detail object). Removal uses the 18a controller's `removing` session and the `Remove service?` dialog already rendered by 18b.

**Tech Stack:** React 19.3.1, CSS Modules, Vitest + jsdom + @testing-library/react + user-event, `installFakeFetch`, `installFakeStream`, `vi.mock('$lib/stacks/cm')`. No new dependencies.

**Spec:** spec §2 goal 1 (parity: guards, lazy editors), §4 (lost guard), §6.1 (`serviceEdit.ts` / `serviceAdd.ts` / `compose/form.ts` reused), §6.4; README right pane ("Edit" in the service header, "+ Add" on the rail), "Fidelity" (where the prototype is silent — editors, dialogs — keep today's Svelte behaviour). **Depends on 18a** (`RemovalSession`, `removeServiceReason`, `LAST_SERVICE_REASON`, controller remove-service methods), **18b** (`ServicePane.editSlot`, `ServiceRail.addSlot`, the `Remove service?` dialog, `guarded`), **18d** (`DiffView`, the `dirty` wiring, `OperationPanel` from 18b).

## Spec divergences

18a's divergences 11, 17 and 18 apply. Additions (author's calls):

1. **The editor replaces the tabs, not the pane**: while `editingService` names the selected service, the service header stays (LED, name, state) with `Edit` swapped for `Close editor` (ghost), and the tab strip and panel are replaced by `ServiceEditor` (fadeUp .18 s); selecting another service, item or chip goes through the guard and closes the editor. The URL does not change for edit mode.
2. **`+ Add` replaces the right pane** with `AddServicePanel` (no service header); the rail keeps its selection; `Cancel` (through the guard) and a successful add return to the previous item; after an add the new service is selected (`?service=<new>`), matching today's "replaces detail and closes panel" plus the design's rail.
3. **`Remove service <name>`** sits in a `footer` of the editor pane as a danger ghost button with `disabledReason` from `removeServiceReason(detail)` (last service) and `aria-label="Remove service <name>"`; the confirm dialog and flow are the 18a controller's. After a successful removal the editor closes and the first service is selected.
4. **`ServiceForm` ids** keep today's `svc-*` ids (`svc-image`, `svc-ports-<i>`, `svc-networks-<i>-name`, …) so labels, `aria-describedby` and the `NetworkPicker` `idPrefix="svc-networks"` contract hold; only one `ServiceForm` is ever mounted on the stack detail (editor or add panel), and Plan 20 renders several with an `idPrefix` prop added here (`idPrefix?: string`, default `svc`).
5. **Network picker slot**: `ServiceForm.networkPicker?: (form: ServiceForm, rowErrors: Record<number, string>) => ReactNode` replaces the Svelte snippet; the editors pass a `NetworkPicker` render function; the form's plain list editor is the fallback when absent or when `networks` is read-only.
6. **Focus management** is kept (preview heading, conflict box, saved heading, first field after Back / Discard, `focusFirstError` on validation and server field errors) with `tabIndex={-1}` hosts and refs; the visually-hidden `role="status"` announcements keep today's sentences.

- Behaviour parity: every string the Svelte tests assert is unchanged (`Preview changes`, `Back to editing`, `Save`, `Apply`, `Reload`, `Discard my changes`, `Open raw YAML editor`, `Open raw YAML editor for <group>`, the `RO_HINT` sentence, `Review changes to <service>`, `Review the service to add`, `Saved <service>. Type the network name instead.`, `Create network…`).
- State machines are reused, not rewritten: `createServiceEdit`, `createServiceAdd`, `validateForm`, `mapServerErrors`, `toForm` / `fromForm` are called exactly as the Svelte components call them; the React components add no validation of their own.
- Dirty flags: `serviceDirty` counts only while `editingService` is set, `addDirty` only while `addingService`; `dirty = composeDirty-branch (18d) || (item is service && editingService && serviceDirty) || (addingService && addDirty)`; `discardAndLeave` clears both and closes both editors; the Apply operation's `done` refreshes stacks and running ops; the editor keeps the user's values across a detail refetch (the `the service editor is mounted from Edit and keeps its state when the stack refetches` case).
- Lifecycle reasons: `Apply` takes `lifecycleReason` from the page (`lifecycleDisabledReason({ live, parseError })`) but **not** the page's busy flag — today's `the service editor Apply is not soft-disabled by a running operation of the page` case; its own `operationRunning` guard stays.
- The Apply operation is tracked (`trackOperation`) like every other start (18a divergence 9) and shown inline through `OperationPanel`.
- Every mutation request carries the hash the preview used; a 409 never overwrites.
- Eagerness: nothing new in the entry; `cm` stays lazy (`DiffView`); entry line recorded per task, unchanged.
- CSS Modules with tokens; `fadeUp` .18 s on the editor pane; classes never asserted.
- Test-first, conventional commits, no code bodies in this plan.

## Review Focus

1. Hash discipline: preview and save carry the same hash, a reload after 409 re-previews with the new hash and the user's values on top, a discard reseeds from the reloaded stack, and the add panel's save carries the previewed hash. (Task 3, Task 4.)
2. Guard integration: a dirty service form or add panel asks before `Edit` of another service, `Logs`, a rail / chip / timeline / tab navigation and a link click; `Discard changes` closes the editor and clears the flag; opening Add while an editor is dirty asks first; a clean editor never asks. (Task 3, Task 4.)
3. Removal flow parity: last-service soft-disable with its reason, double confirm → one `DELETE` with `aria-busy`, the 409 reload outcomes (confirm again / last / missing / failed), the dependency refusal, a cancelled session's late response, and a pending detail read never overwriting an accepted result — all through the dialog on the page. (Task 3.)
4. Picker and browser safety: network list fetched once per mount, `Create network…` restores the previous selection on cancel and selects the created network after a delayed reload, a delayed cancelled POST never changes rows or closes a newer dialog; the browser ignores stale directory responses, keeps focus inside the dialog, and words 403 / 404 correctly. (Task 1.)
5. Form correctness: read-only groups are uneditable and sent unchanged, errors land on the right control with `aria-invalid` and a linked message, hidden-source errors are not counted, the announcement names fields by label, `.env` paste splits rows only into an empty editable row. (Task 2.)
