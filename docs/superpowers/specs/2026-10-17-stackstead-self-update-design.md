## Recommended scope and trust policy

Implement a manually triggered stable-release update from Settings for every existing installer format: Linux script, DEB, RPM, macOS script and PKG. A separately supervised trusted updater survives stopping the web server. It accepts only bounded update requests over authenticated local IPC, uses a fixed official release source, and chooses the matching native install format. The web server retains its current identity and hardening. No browser sudo password, setuid workaround, arbitrary URL, arbitrary path, arbitrary command, or Docker-based host escalation.

Default to the project's existing distribution trust contract: HTTPS to the fixed `rcss-labs/stackstead` GitHub release source plus strict SHA256SUMS verification. This is a compatibility decision, not publisher authentication: someone who controls both official assets and checksums can publish executable code, just as with today's root installer. State that existing limit in the security documentation. Revalidate downloads in the helper; a web-supplied hash is never authoritative. This supports existing release practice without inventing a signing prerequisite. Signed metadata with an embedded public trust root is a valuable separate enhancement; existing optional SSH signing machinery can inform it, but key generation, custody and release-policy changes need an explicit future decision. Never claim a GitHub asset digest or unsigned checksum authenticates a publisher independently.

Initially expose stable versions only, explicit Check for updates and Update buttons, no scheduled automatic install, no arbitrary downgrade or channel selection. Same/older versions are non-updates. A failed transaction may reinstall its one recorded previous package as bounded recovery. Keep existing command-line/manual installation paths working.

“All installers” describes install formats, not an ability to discover and control arbitrary custom supervisors. For the script's documented non-systemd mode, define and implement an operator-installed root-owned supervisor integration contract. Until registered and healthy, show actionable setup-required status. This is a real limitation requiring clear documentation, not an unsupported-format exclusion. If the intended acceptance criterion is zero setup on every non-systemd supervisor, that is additional unspecified platform work and cannot honestly be promised by this design.

## Evidence and exact integration seams

- `deploy/systemd/stackstead.service`: dedicated `stackstead` UID, supplementary docker group, `NoNewPrivileges=true`, `ProtectSystem=full`, empty capabilities. It cannot safely replace `/usr/bin` or `/usr/local/bin` by spawning an ordinary child. Docker membership is already root-equivalent, but must not become the updater mechanism.
- `install.sh`: `--prefix`, `--no-start`, `--root`, `--from-pkg`, explicit checksum verification, package ownership refusal, systemd unit path rewriting, stopped-service preservation, macOS `as_user`/`priv` separation. Non-systemd prints “start it under your own supervisor.” Root never writes the target user's home in the macOS design; preserve that invariant.
- `deploy/nfpm.yaml`: DEB/RPM own `/usr/bin/stackstead` and `/usr/lib/systemd/system/stackstead.service`; config is `config|noreplace`. Add the helper binary, updater service/socket artifacts and root-owned registration location here.
- `deploy/pkg/deb/postinst` and `deploy/pkg/rpm/post`: upgrades currently `try-restart`; a managed update must suppress this restart using a root-owned transaction context, because the updater must control backup/migration/probation ordering. Preserve existing behavior for external manual upgrades. `prerm`/`postrm` and RPM `preun`/`postun` own removal semantics; add helper lifecycle and active-transaction guards. Debian remove preserves state/config, purge removes state/config; RPM removal preserves them. Never remove `/opt/stacks`.
- `deploy/macos/launchagent.plist.in`: web server is a per-user LaunchAgent. Add a separate root LaunchDaemon for the helper, without converting the application to a root service.
- `deploy/macos/scripts/postinstall`: currently selects `/dev/console` user and delegates home setup as that user. A managed PKG upgrade must use registered target UIDs, not silently choose whichever user happens to own the console. Staged/non-boot-volume packages must remain staged-only.
- `Makefile`: builds four tar targets, DEB/RPM and a universal macOS PKG. Add helper build artifacts to all formats. `tools/mkrelease` and associated verification tooling produce/check sums; extend coverage to helper payload and optional future metadata. Releases are intentionally unsigned today (`deploy/release/RELEASING.md`).
- `internal/cli/serve.go:96`: holds `DataDir/stackstead.lock` for server lifetime. `store.Open` migrates before the HTTP server starts. `serve.go:240` drains HTTP, cancels Compose operations, stops background collectors and closes DB; containers themselves remain running. Add maintenance admission and boot/probation handshake here.
- `internal/store/store.go`: ordered SQLite migrations, refusal of newer schemas, `SupportedSchema`, `QuickCheck`, `Backup` via `VACUUM INTO`. `internal/cli/cmd_db.go`: verified online backup, stopped-server exclusive restore, WAL/SHM preservation and swap recovery. Extract reusable ownership-aware snapshot/restore routines rather than reimplementing them in shell or executing an untrusted installed program as root.
- `internal/stacks/ops.go`: in-memory operation tracking dies with the process. Do not use it as the durable update job store; reuse conventions only. Add a shared maintenance admission gate across stack/container/network mutators, not only the update endpoint.
- `internal/api/server.go`: extend `Options` with an `UpdateAPI` interface, independently of Docker/Observe availability; register authenticated update routes. `session.go` supplies `requireSession`; `auth/service.go` explicitly implements one admin, so an authenticated session is the existing admin authorization model. Add same-origin/CSRF protection to new state-changing update endpoints; do not assume SameSite alone solves all origins/deployments.
- `internal/api/handlers_auth.go:19`: public `/api/health` only returns liveness, and must remain non-sensitive. `internal/api/stacks.go` status route and `status_version_test.go` already report authenticated version. Add helper-only authenticated boot identity/readiness, not unauthenticated version disclosure.
- `internal/version/version.go`, `internal/cli/cmd_version.go`: existing version/commit/OS/arch metadata; extend with explicit update/DB compatibility information where needed. A version string or `/api/health` alone cannot prove the new process serves the port.
- `web/src/routes/Settings.svelte`, `Settings.test.ts`: add Update Stackstead card near application status, using existing `Button`, `Banner`, `ConfirmDialog` and API patterns. Add DTO/client methods in `internal/apitypes/types.go`, `internal/client/client.go`, and `web/src/lib/api/client.ts`/types. CLI local recovery belongs under a bounded new host update command registered in `internal/cli/commands.go`; remote settings update commands can share API later if in scope.

## Components and permissions

Use a dedicated Go helper executable, not a broad root mode of the web application. Shared updater packages handle download/verification, transaction state and adapter contracts; privileged entrypoint includes only required functionality. Linux helper code lives in a root-controlled libexec path and root service; macOS uses `/Library/PrivilegedHelperTools` plus `/Library/LaunchDaemons`. App prefix can vary; helper trust storage must never be under a user-writable prefix, home, app data directory, or Docker volume.

Root-owned registration records installer kind, canonical binary/prefix, expected service identity, config/data instance references, allowed client UID, supervisor adapter, ownership expectations and protocol versions. It is produced at install/bootstrap, not inferred from browser parameters or trusted from app-writable config. Reconcile package ownership on every preflight; conflicting ownership fails before stop. Do not follow symlinked path components into privileged writes. Validate parent directories; for legacy macOS prefixes writable by ordinary users, never execute binaries/scripts from that prefix as root. Stage verified helper/package artifacts in a root-private tree and run user-specific DB/config operations after dropping to the registered UID. Paths under user homes are handled only under that UID. Do not “fix” `/usr/local` ownership globally.

Local IPC: Unix stream socket in a root-owned runtime directory, filesystem permissions restricted to the registered service identity plus OS peer credentials (`SO_PEERCRED` Linux; platform peer UID check on Darwin). Both ends authenticate expected UID; socket permissions alone are insufficient as a portable security mechanism. On macOS allow only registered UIDs, separate instance permissions, bounded job visibility. A compromised registered app user can request an official update, but cannot select a command, path, download host, or another instance. Do not claim peer UID identifies one executable uniquely.

Minimal helper requests: capability/status, resolve/check, begin using a previously issued candidate ID + idempotency key, job status; cancel only before destructive phase. Client never supplies shell, install arguments, supervisor executable, arbitrary release URL, arbitrary destination or credential. Strict message size/deadline limits. Root-owned journal has no browser session secrets and survives app DB restore.

Use one update lock per shared installation, plus per-instance admission/DB locks. No two update jobs, no overlap with uninstall, and no concurrent binary writer. Respect package-manager locks; report busy rather than deleting locks or killing package tools. Process environment/PATH is fixed and stripped of caller influence. All subprocess execution uses fixed executable paths and argv without shell interpretation. Fixed GitHub origins and tightly validated HTTPS asset redirects; downloads are bounded, private, exclusive and verified before extraction/execution. Tar extraction rejects traversal, absolute paths, links and unexpected types/files.

DEB/RPM in chroots/non-systemd also retain current staged behavior; an active non-systemd deployment requires the same explicit supervisor contract. `--root` must only stage helper/config artifacts and print service operations; never start a host helper. `--no-start` must not accidentally start the application; starting the independent helper for future updates is a separately documented installer default and should have an explicit opt-out. Existing stopped/disabled applications are never started just to satisfy health checks; local CLI update can finish as installed-pending-start, while an active web request necessarily originated from a running instance.

A shared macOS prefix means updating the binary affects every user. Enumerate registered instances and preflight them together, block mutators and snapshot each DB under its UID; restart only loaded/running agents. Unregistered running instances must block update with explicit administrator recovery instructions, rather than migrating an unknown user's DB. A simple single registered-user implementation must explicitly detect shared usage and block it until coordinated support exists; it cannot be called complete all-installers support while silently risking other agents.

## Durable transaction and database safety

Durable root-private state machine: accepted → resolving → downloading → verified → preflighted → quiescing → stopped → snapshotted → installing → starting-probation → verifying → succeeded; failure branches before install leave old deployment running; after install proceed rolling-back → rolled-back, or recovery-required. Every transition records job ID, immutable candidate/hash, old/new identity, artifact paths/hashes, config/data instance IDs, original supervisor states and backup identity. Write/fsync journal and parent directory before irreversible steps; use exclusive staging, versioned files and checksummed state. No credentials or full sensitive logs in browser/job record.

1. Resolve candidate through fixed public GitHub endpoint. Validate stable semver, supported OS/arch, non-draft/non-prerelease, required matching assets and helper protocol. Cache with bounded TTL and explicit refresh; GitHub rate-limit/network failure is an error/retry state, never “up to date.” Pin candidate version and checksums; installation must not re-resolve `latest` after the user confirms.
2. Download new artifact and authenticated-to-current-policy previous artifact before stopping. Existing prior artifacts without signature remain valid under the current HTTPS+SHA policy; retaining exact previous installed binary too helps diagnostics but is not a replacement for native package rollback. Verify disk space for downloads, installation, DB snapshots and rollback.
3. Preflight config under app UID, ownership, package health/locks, supervisor adapter and helper protocol. Refuse unknown install mode or unrecoverable configuration. All running Compose/container/network actions must finish before admission closes; recommend refuse/update-later while an operation is active, rather than canceling it unexpectedly. Freeze new app writes throughout probation, including account/settings changes, expired-session cleanup triggered by authenticated GETs, startup `stackSvc.Sync(ctx)` registry writes, and metric/background or lazy request-triggered writers. Reads remain available; an expired session still returns 401 while its deletion is deferred. Migration is the allowed probation write; stack sync and ordinary writers start only after release.
4. Stop via supervisor and confirm expected process stopped and data lock obtainable. Take final verified SQLite snapshot only after writers stop, using SQLite and existing ownership/WAL protections. An online snapshot taken before quiescence is insufficient for zero-loss rollback. Preserve original config and record hash; normally do not edit it. Never snapshot only `stackstead.db` with `cp` while WAL writers are live.
5. Release any DB lock only at the controlled startup boundary. Install matching format with helper-controlled package scripts, not raw installer rerun from app-controlled path. Preserve configs, DB, stack files and Docker state. No container recreation/stopping is part of updating Stackstead.
6. Start in probation with job/boot nonce and maintenance admission retained. `store.Open` currently migrates at startup: new startup must establish probation before accepting mutators or starting background writes. Compare readiness identity/version/commit, instance/config identity and supervisor process identity against expected job; public 200 health is insufficient. Docker unavailable is a valid degraded app state, not a reason to roll back a healthy Stackstead.
7. Only after every active instance passes readiness and DB checks, atomically commit success and lift maintenance. Then run deferred stack registry sync and start collectors/background writers. Persist the job-specific probation ticket before each boot; target boot expects the target identity, rollback boot a fresh nonce and the previous identity. Release receives that durable job identity even after helper restart. A release-notification failure after commit is retried/reconciled, never grounds for snapshot restore; committed Startup is ordinary so the app cannot remain frozen indefinitely. After this point no automatic rollback to the pre-update snapshot: that would discard valid new writes. A later downgrade is a separate manual recovery operation.
8. On pre-commit failure, stop new processes, restore original package/payload and the matching pre-migration DB under app UID with exclusive lock, archive failed DB/WAL/SHM for diagnosis, restore original service states, prove old identity/DB health. Preserve failure job/logs. If rollback package install or DB restore fails, enter recovery-required and never claim success. Expose exact local recovery instructions and durable local status because the web UI may be unavailable.

Do not depend solely on schema equality for rollback: later application semantics can alter same-schema data. Snapshot restoration is safe before commit because no user writes were accepted. Future releases should declare required helper protocol and supported migration ranges; explicit compatibility checks reject unsupported direct jumps rather than learning after half-install. A release that changes rollback requirements must supply the information needed before stopping.

The helper survives web restart by being a separate service. Its own package upgrade must not kill the active transaction: upgrade scripts do not restart a busy updater; running old helper completes only if target protocol is supported, commits journal, then performs a supervised idle restart into the verified new helper. Native package removal during a live job must fail before deleting helper/data. External package operations and helper locks need tested ordering so guards do not deadlock a helper-owned package transaction.

Bind and serve authenticated helper IPC before recovering unfinished jobs. Startup, status and job reads use bounded consistent durable snapshots without acquiring the installation mutation lock, because recovery may hold it while starting an app that must negotiate probation before migration. New Begin/work stays busy or recovery-required until recovery is safe. The coordinator owns persisted tickets; app-control Prepare merely applies an existing ticket to a live app and does not write the root journal.

Managed package scripts call the pinned worker through the private bootstrap for a read-only lifecycle probe: validate context/ownership/protocol/live worker/package ancestry/expected version without reacquiring either the parent's installation lock or a native package lock, mutating state, or starting recovery. Separate helper-owned external-operation reservations span validated native package-tool lifetime; external guards inside package transactions acquire the installation reservation nonblockingly or fail busy, never wait in the opposite lock order. Begin checks reservations before mutations. Snapshot/restore runs through a bounded trusted helper child under the registered UID/GID, with validated bounded backup handles/streams; root never performs app home/config/data access or executes a user-prefix app binary for those operations.

After power loss: resume by journal phase and observed package/file/DB state, never blindly repeat install or restore. Pre-install phases can discard incomplete staging and keep old version; stopped/snapshotted phases can restore/start old; installing phase inspects package state before bounded repair or recovery-required; probation with no durable commit rolls back; durable success never restores the old snapshot. Recovery actions must remain local when web is unavailable. Full power-fail transactional guarantees across package DB, filesystems and app DB cannot be obtained by a single rename; the explicit repair state is part of correctness.

## Settings/API behavior

`GET /api/settings/update` returns current build, installer kind, capability (`ready`, `setup-required`, `disabled`, `busy`, `recovery-required`), reason/actionable bootstrap instructions, candidate and last/current job. `POST /api/settings/update/check` refreshes fixed-source metadata. `POST /api/settings/update` requires authenticated admin, same-origin/CSRF validation, bounded candidate ID and idempotency key, and returns 202 with durable job ID. `GET /api/settings/update/jobs/{id}` returns sanitized progress. Helpers enforce allowed candidate independently; API is not the privilege boundary.

The update origin check uses the request Host, never a forwarded host. Support direct HTTP/TLS and the documented loopback TLS reverse proxy: a single `X-Forwarded-Proto: https` is honored for scheme only from a loopback proxy peer; ambiguous values and nonloopback scheme spoofing are rejected. No existing trusted-proxy configuration is assumed. No-newer-release is a successful status without a candidate; release-source failure is an error/retry state.

Card states: checking, current, update available (current → target + release notes link), updating with stage, reconnecting while server is stopped, succeeded with proven version, rolled back with error, setup-required with exact documented one-time terminal setup, and recovery-required. Confirm update explains brief UI interruption, stacks keep running, and automatic pre-commit recovery. Lost HTTP connection during restart is expected; reconnect polling uses bounded backoff and job identity, and auth expiration requests login rather than declaring failure/success. No need for SSE across restart; polling is simpler and durable. No arbitrary release-note HTML rendering.

## Threat model and bounded failures

Protect against unauthenticated/cross-origin requests, nonregistered local users, replay/double-click, web-supplied command/URL/path injection, tampered staging/symlinks, malformed/oversized archives, metadata changing between check and install, wrong arch/version/package, stale health answers, concurrent operations/package changes, loss of process/power during each state, failed migration, and partial rollback. A compromised admin/app UID can request an allowed official update; the helper should expose no broader root functionality. Current Docker access and official-release compromise remain existing high-trust boundaries, explicitly documented. Do not pretend the helper provides isolation from an attacker who already controls Docker or root.

## Practical implementation sequence and ownership

Planning and design checks use GPT-6.1 Sol high per the user's explicit override. Implementation uses the project's normal worker tiers (Sol medium for integration work, Sol low only for mechanical edits); task reviews use Sol high. The user's override applies to planning; it does not imply an unrequested change to all later model roles. No Astra planning delegation. Parent can execute inline instead of creating agents.

1. **Contract and compatibility fixtures.** Define installer registration/protocol/job DTOs, maintenance admission, recovery invariants and cross-platform adapter interfaces; create test fixtures representing current script/DEB/RPM/PKG installations. Acceptance: ambiguous/unknown registrations and unauthorized requests fail before mutations. Record current trust policy and explicit no-systemd integration contract.
2. **Release client and artifact verifier.** Add fixed-source stable candidate resolver/downloader, strict checksum/extraction checks and immutable candidate IDs; integrate existing release filenames/tooling. Acceptance: release/transport tests above, no privileged action on invalid artifact. No new dependency without targeted maintenance/security assessment; existing stdlib plus x/sys already in module should cover most work.
3. **Durable helper and IPC.** Add separate helper command, platform peer auth, private journal/lock and read-only capabilities. Acceptance: authorization, idempotency, persistence and fault-injection tests. Do not yet wire real install actions until test adapters prove transaction ordering.
4. **Maintenance, snapshot and probation.** Extract existing backup/restore primitives; add app mutator/background write admission and helper-only boot/readiness handshake. Acceptance: migration rollback, WAL correctness, no pre-commit writes, old health spoof rejection. This is prerequisite to enabling install adapters.
5. **Linux script/systemd and custom supervisor support.** Add helper payload/unit/registration/bootstrap/uninstall to script, bounded tar installation, OpenRC example plus root-owned custom supervisor adapter contract. Acceptance: existing installer regressions plus real systemd and Alpine lifecycle paths.
6. **DEB/RPM native package adapters and lifecycle.** Extend nfpm/scripts, implement managed transaction context and safe helper handoff, retain previous package, test lock ordering and interrupted package states. Acceptance: name/arch/version/ownership retained; ordinary package-manager upgrade/removal behavior unchanged; native rollback and recovery-required proven for each format.
7. **macOS script and PKG support.** Add daemon/root-owned storage, target UID registrations, per-user actions, shared-prefix coordination and receipt-preserving PKG path. Acceptance: current home-safety tests plus real update/rollback receipt behavior and multiple-user cases. Do not mark this format complete based on Linux cross-build alone.
8. **Settings/API.** Add authenticated endpoints/client/types and card with confirmation/progress/reconnect/recovery. Acceptance: focused API/Settings tests and an end-to-end interrupted/reconnected update against fake adapter; then native end-to-end update per matrix.
9. **Integrated review, documentation and release rehearsal.** Sol high verifies red/green evidence, security constraints, all installers, recovery and remaining failures. Update install/security/API/release docs with helper privilege, bootstrap, unsigned trust, custom supervisor contract and local recovery. Run checks once at appropriate breadth; do not expand test scope after passing without a concrete concern.

Tasks 2 and initial parts of 3 can be independent after contract agreement; Linux/macOS adapter work can proceed independently after transaction/protocol stabilize. Shared transaction/DB code should have one owner to avoid incompatible recovery assumptions. No production installation is necessary to make code/tests/design reviewable.

## Decisions and limitations for parent to record

Routine recommended defaults: stable manual updates, official source only, existing HTTPS+SHA trust, native format preservation, one retained prior artifact + DB snapshot, maintenance admission, brief downtime, automatic rollback only before commit, no background auto-installs. These follow existing behavior/scope and need no additional question if user already delegated implementation choices.

Material assumption to state clearly: non-systemd/custom supervisors require one-time administrator registration of the helper and supervisor adapter; old 0.2.0 installs of every format require one manual bootstrap upgrade. The current web process cannot grant itself the privilege/supervision files absent from old installers. There is no honest purely in-browser bootstrap for those old installs.

Future optional decisions: publisher signing/key custody, scheduled auto-updates, other channels, additional turnkey supervisor integrations. These do not block implementing the requested baseline. A release with missing native artifact, broken helper protocol, unknown package state, unavailable prior rollback artifact, unsafe writable helper path or unregistered shared instance is blocked with a precise recovery/setup reason, not silently treated as up-to-date or supported automatic success.

### Recovery when the updater package changes

The supervised entry point must not depend solely on the package-owned helper executable that an in-flight package transaction may replace/remove. Installers provision a root-owned bootstrap copy in updater-private storage (Linux `/var/lib/stackstead-updater/bootstrap/v1/`, macOS `/Library/Application Support/StacksteadUpdater/bootstrap/v1/`). The independent systemd/LaunchDaemon/custom-supervisor configuration invokes that copy. Package payloads supply new helper builds, but an active transaction never overwrites its bootstrap or pinned worker. Every path component is root-owned and not writable by registered application users; updater-private storage remains separate from application data and user homes.

Before any service stop or installation, copy the currently trusted worker to an immutable versioned path under updater-private `workers/<sha256>/`, verify/hash it, fsync it, and durably record its digest, journal protocol, installation ID and job ID. Bootstrap protocol v1 reads only a bounded v1 journal and chooses either that pinned recovery worker for an unfinished job or the recorded active idle worker. It derives worker paths from validated digests rather than executing an arbitrary journal path. Both bootstrap and worker validate ownership, regular-file type and expected digest. Package scripts suppress helper restart/deletion while this managed transaction is active. Bootstrap/worker removal during external uninstall is refused before removal if the lock is active; remove/purge handles the known private artifacts only when idle.

After durable transaction success or verified rollback, activate the matching helper for the installed application and perform any required supervised idle restart. A later bootstrap protocol upgrade must be its own idle, backward-compatible transition; it cannot discard v1 recovery while a v1 job exists. Rollback to a prior updater-enabled package must leave the pinned worker/bootstrap and its journal available until recovery completes. The previous worker is retained until the completed job can no longer need recovery.

This is a process/reboot recovery guarantee while the root-owned bootstrap and supervisor remain intact. Disk corruption, deletion by root, unavailable filesystems, or a damaged native package database may still require explicit local repair. `recovery-required` is a first-class outcome; the design does not claim atomicity across the package database and filesystem or promise automatic repair of every failed package transaction.

### Compatibility metadata and the first supported release

Every updater-enabled release must ship `stackstead-update.json`, listed in `SHA256SUMS`, with a strict schema version 1. Required fields describe: exact release version and full source commit; helper request-protocol minimum/maximum; bootstrap and journal protocol versions; migration source-schema minimum and target schema; and the exact asset names for each supported OS/architecture/installer format. Its `ReleaseIdentity { Version, Commit string }` is platform-neutral: one manifest serves the full asset matrix and never inherits the builder host's OS/arch. Candidate/registration/probation/readiness use selected executable `Identity { Version, Commit, OS, Arch string }`; a universal PKG asset label remains `universal` while selected executable arch is concrete `amd64` or `arm64`. The release builder derives the database schema from compiled source, never from a manually maintained independent constant. The manifest references existing archive/DEB/RPM/universal-PKG assets; it does not change the chosen HTTPS+checksum trust policy or introduce signing keys.

For protocol v1, unknown schema/journal/bootstrap major versions, incompatible helper ranges, absent native-format assets, malformed metadata, or an installed database outside the migration range all refuse the update before stopping the application. A candidate's immutable ID binds its release identity and verified metadata/checksums; neither the browser nor the installer re-resolves `latest` after confirmation. Current metadata version/full commit must match the current installed app; target metadata must match the staged target app, with selected OS/arch checked separately and helper ranges checked against the actual pinned worker. Different releases need not share a commit. The manifest is checked against native package metadata too, not accepted as proof on its own. Database migration can still fail on actual data; the pre-commit snapshot and probation protocol cover that case.

The first release providing this feature is the baseline for managed web updates. Installation of that release from v0.2.0 or earlier uses the existing manual installer/package path once; no automatic recovery or web-update guarantee is retroactively claimed for that bootstrap. All later web updates require both a compatible target manifest and a compatible previous updater-enabled release with its exact verified rollback artifact. A source/previous release without metadata, including v0.2.0, cannot participate in an automatic managed transaction and reports setup/recovery-required as appropriate. Do not attempt native downgrade into a pre-updater package whose scripts cannot honor maintenance and helper retention.

Release rehearsal fixtures must therefore use an updater-enabled baseline and candidate (for example v0.3.0 → v0.3.1), while separate installer regressions prove manual v0.2.0 → first-updater-release bootstrap. Test that reboot recovery still works after the package-owned helper payload is replaced, that rollback leaves the old compatible package plus restored schema, and that missing/incompatible metadata causes zero service stops and zero installation calls.
